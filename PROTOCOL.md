# Описание протокола обмена MFTP/1

*(раздел для пояснительной записки к лабораторной работе)*

## 1 Назначение и транспорт

Протокол MFTP/1 (Mini File Transfer Protocol, версия 1) предназначен для обмена файлами между клиентским приложением и сервером файлового хранилища. Протокол является прикладным и функционирует поверх транспортного протокола TCP стека TCP/IP. По умолчанию сервер принимает соединения на TCP-порту 2121.

В отличие от классического FTP (RFC 959), использующего два соединения (управляющее и канал данных) и текстовые команды, MFTP/1 использует одно TCP-соединение, по которому в обоих направлениях передаются бинарные кадры (frames). Команды и файловые данные мультиплексируются в одном потоке, что упрощает прохождение через NAT и TCP-туннели (CloudPub), так как требуется проброс только одного порта.

Обмен ведётся по схеме «запрос — ответ»: клиент отправляет кадр-запрос и ожидает ровно один кадр-ответ, после чего может отправить следующий запрос. Одно соединение соответствует одному сеансу пользователя.

## 2 Структура кадра

Каждый кадр состоит из трёх частей: фиксированного заголовка длиной 16 байт, блока метаданных переменной длины и блока полезной нагрузки (payload) переменной длины. Многобайтовые целые числа передаются в сетевом порядке байтов (big-endian). Структура заголовка приведена в таблице 1.

Таблица 1 — Структура заголовка кадра

| Смещение, байт | Размер, байт | Поле | Тип | Описание |
|---|---|---|---|---|
| 0 | 2 | magic | ASCII | Сигнатура протокола, значение «MF» (0x4D 0x46) |
| 2 | 1 | version | uint8 | Версия протокола, значение 1 |
| 3 | 1 | opcode | uint8 | Код операции (таблица 2) |
| 4 | 1 | status | uint8 | Код состояния (таблица 3); в запросах равен 0 |
| 5 | 1 | flags | uint8 | Зарезервировано, равно 0 |
| 6 | 2 | meta_len | uint16 | Длина блока метаданных, байт (0…65 535) |
| 8 | 8 | payload_len | uint64 | Длина полезной нагрузки, байт |

Непосредственно за заголовком следуют:

- блок метаданных длиной meta_len байт — JSON-объект в кодировке UTF-8, содержащий параметры команды (путь, размер файла, контрольную сумму и т. п.);
- блок полезной нагрузки длиной payload_len байт — «сырые» двоичные данные (содержимое файла или список каталога).

Разделение команд и данных обеспечивается за счёт явного указания длин в заголовке (length-prefixed framing): получатель сначала читает ровно 16 байт заголовка, затем ровно meta_len байт метаданных, затем ровно payload_len байт данных. Признак конца кадра и экранирование не требуются, поэтому файлы любого содержимого передаются без преобразования. Поле payload_len разрядностью 64 бита позволяет передавать файлы размером более 4 ГБ (на сервере установлено защитное ограничение 4 ГиБ на один кадр).

Метаданные передаются в текстовом формате JSON, что обеспечивает расширяемость протокола (добавление новых параметров не меняет формат заголовка), а данные файлов — в двоичном виде, что исключает накладные расходы на кодирование (например, Base64 увеличил бы объём на 33 %).

## 3 Коды операций

Коды операций приведены в таблице 2. Коды 0x01–0x0F используются в запросах клиента, коды 0x80 и выше — в ответах сервера.

Таблица 2 — Коды операций

| Код | Мнемоника | Направление | Метаданные запроса | Полезная нагрузка |
|---|---|---|---|---|
| 0x00 | HELLO | сервер → клиент | server, proto, nonce | нет |
| 0x01 | AUTH | клиент → сервер | user, password, key_id, key_proof | нет |
| 0x02 | LIST | клиент → сервер | path | нет |
| 0x03 | UPLOAD | клиент → сервер | path, size, sha256, overwrite | содержимое файла |
| 0x04 | DOWNLOAD | клиент → сервер | path | нет |
| 0x05 | DELETE | клиент → сервер | path, recursive | нет |
| 0x06 | MKDIR | клиент → сервер | path | нет |
| 0x07 | PING | клиент → сервер | — | нет |
| 0x0F | BYE | клиент → сервер | — | нет |
| 0x80 | OK | сервер → клиент | результат операции | нет |
| 0x81 | ERROR | сервер → клиент | message | нет |
| 0x82 | DATA | сервер → клиент | описание данных | список каталога (JSON) или содержимое файла |

## 4 Коды состояния

Поле status ответа ERROR содержит машиночитаемый код причины отказа (таблица 3), поле message метаданных — текстовое описание.

Таблица 3 — Коды состояния

| Код | Наименование | Значение |
|---|---|---|
| 0x00 | SUCCESS | Операция выполнена |
| 0x01 | BAD_REQUEST | Некорректный запрос |
| 0x02 | AUTH_REQUIRED | Команда требует аутентификации |
| 0x03 | AUTH_FAILED | Неверный логин или пароль |
| 0x04 | KEY_REJECTED | Аппаратный ключ отсутствует или недействителен |
| 0x05 | NOT_FOUND | Файл или каталог не найден |
| 0x06 | ALREADY_EXISTS | Объект уже существует |
| 0x07 | FORBIDDEN | Доступ к пути запрещён |
| 0x08 | TOO_LARGE | Превышен допустимый размер / нет места |
| 0x09 | CHECKSUM_MISMATCH | Контрольная сумма не совпала |
| 0x0A | RATE_LIMITED | Превышено число попыток / сервер перегружен |
| 0xFF | INTERNAL | Внутренняя ошибка сервера |

## 5 Установление сеанса и аутентификация

Аутентификация двухфакторная: пароль (фактор знания) и аппаратный USB-ключ (фактор владения). Последовательность установления сеанса:

1. Клиент устанавливает TCP-соединение с сервером.
2. Сервер отправляет кадр HELLO, метаданные которого содержат одноразовое случайное число nonce длиной 32 байта (в шестнадцатеричной записи).
3. Клиент считывает с USB-накопителя файл ключа `.auth_token.key`, содержащий идентификатор key_id и 256-битный секрет, и вычисляет доказательство владения ключом:
   key_proof = HMAC-SHA256(secret, nonce ‖ user).
4. Клиент отправляет кадр AUTH с логином, паролем, key_id и key_proof.
5. Сервер проверяет пароль по хранимому хэшу PBKDF2-HMAC-SHA256 (200 000 итераций, индивидуальная соль) и вычисляет ожидаемое значение HMAC по хранимому секрету. Сравнение выполняется за постоянное время.
6. При успехе сервер отвечает OK; при неверном пароле — ERROR с кодом AUTH_FAILED, при неверном или отсутствующем ключе — ERROR с кодом KEY_REJECTED.

Секрет ключа по сети не передаётся. Поскольку nonce уникален для каждого соединения, перехваченное значение key_proof не может быть использовано повторно (защита от атаки повторного воспроизведения). Таким образом, знание пароля без физического наличия флешки с ключом не позволяет получить доступ.

Файл ключа имеет текстовый формат: строка-сигнатура `MFTP-KEY v1`, затем поля `user`, `key_id`, `secret` (Base64) и `check` — SHA-256 от остальных полей для контроля целостности. Клиент принимает ключ только с накопителей типа «съёмный диск».

Для защиты от подбора пароля сервер разрывает соединение после трёх неудачных попыток и блокирует учётную запись на 60 с после пяти неудачных попыток. Блокировка привязана к логину, а не к IP-адресу, так как при работе через туннель все клиенты имеют адрес туннельного агента.

## 6 Передача файлов

**Загрузка на сервер (UPLOAD).** Клиент вычисляет SHA-256 файла и отправляет кадр, в метаданных которого указаны путь назначения, размер и хэш, а в полезной нагрузке — содержимое файла (payload_len = size). Сервер принимает данные блоками по 64 КБ во временный файл, параллельно вычисляя SHA-256, сверяет его с переданным значением и атомарно переименовывает временный файл в целевой. Незавершённая передача не оставляет на сервере повреждённого файла.

**Скачивание (DOWNLOAD).** Клиент отправляет кадр с путём файла. Сервер отвечает кадром DATA, в метаданных которого указаны имя, размер, SHA-256 и время модификации, а в полезной нагрузке — содержимое файла. Клиент принимает данные во временный файл, проверяет хэш и переименовывает файл.

**Список каталога (LIST).** Ответ DATA содержит в полезной нагрузке JSON-массив записей `{name, type, size, mtime}`. Список передаётся в payload, а не в метаданных, чтобы не ограничивать число файлов в каталоге размером поля meta_len.

Пример кадра запроса UPLOAD файла размером 1 048 576 байт (шестнадцатеричная запись):

```
4D 46 01 03 00 00 00 83 00 00 00 00 00 10 00 00   заголовок (16 байт)
7B 22 70 61 74 68 22 3A ... 7D                     meta (131 байт JSON)
.. .. .. ..                                        payload (1 048 576 байт)
```

Расшифровка: «MF», версия 1, opcode 0x03 (UPLOAD), status 0, flags 0, meta_len = 0x0083 = 131, payload_len = 0x100000 = 1 048 576. Метаданные: `{"path":"/docs/a.bin","size":1048576,"sha256":"<64 hex-символа>","overwrite":false}`.

## 7 Синхронизация потока и обработка ошибок

Если сервер отклоняет запрос с полезной нагрузкой (например, UPLOAD в существующий файл без флага overwrite), он всё равно вычитывает payload_len байт из соединения и лишь затем отправляет ERROR. Тем самым граница следующего кадра сохраняется, и сеанс может быть продолжен. Ошибки разбора заголовка (неверная сигнатура или версия) считаются фатальными: соединение закрывается, так как восстановить границы кадров невозможно. Пути, переданные клиентом, приводятся к домашнему каталогу пользователя; попытки выхода за его пределы (`../`) отклоняются с кодом FORBIDDEN.

## 8 Многопоточная обработка на сервере

Сервер реализован на языке Python на основе класса `socketserver.ThreadingTCPServer`: для каждого принятого TCP-соединения создаётся отдельный поток, в котором выполняется цикл чтения кадров и обработки команд. Потоки разных клиентов работают независимо, поэтому длительная передача файла одним клиентом не блокирует остальных. Число одновременных сеансов ограничено семафором (по умолчанию 32); при превышении новый клиент получает ERROR с кодом RATE_LIMITED. Разделяемые структуры (хранилище учётных записей, счётчики неудачных попыток) защищены блокировками `threading.Lock`. Неактивные соединения закрываются по таймауту (300 с), клиент поддерживает сеанс кадрами PING раз в 60 с.
